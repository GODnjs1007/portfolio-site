### 목표

- 목적 : 환자 수를 6→20→50→100명으로 늘리면서 끝단 지연, 유실을 재고 서버가 어디서 못 버티는지 찾음. 숫자를 눈으로 보려고 모니터링 추가
    - 단계 흐름 : 4단계 = 처음 끝까지 연결 (20명) / 5단계 = 환자 수 늘리고 한계점 찾기
    - 측정 도구 : 보내는 구간은 3단계 D 측정용 수신기, 끝단은 워커 로그
- 흐름 : A: 모니터링 붙이기 → B: 환자 수별 측정 → C: 100명에서 w0만 밀린 이유 → D 환자 상태 화면

### A. 모니터링 붙이기

- 목적 : 부하테스트 중에 CPU, 메모리, 큐 길이를 그래프로 보려고 모니터링을 붙임
    - 앱 코드는 안 건드리고 기존 도커 컴포즈 위에 얹음
- 설명 : exporter들이 숫자를 내놓으면 → prometheus가 5초마다 가져가서 저장 → Grafana가 그래프로 보여줌
    - prometheus : 숫자를 5초마다 모아 저장하는 창고 (포트 9090)
    - Grafana : 창고 숫자를 그래프로 보여주는 화면 (포트 3000)
    - exporter : 숫자를 내놓는 프로그램
        - node-exporter : VM 전체 CPU , 메모리
        - cAdvisor : 컨테이너별 CPU, 메모리
        - redis-exporter : 큐 길이
    - 가져가는 방식 : prometheus가 각 주소의 /metrics 페이지를 직접 가지러 감.
        - exporter가 보내주는 게 아님
    - prometheus.yml : Prometheus가 어디서 숫자를 가져올지 적는 목록
        - job_name : 대상 이름
        - targets : 주소:포트
    - 접속 방법 : 맥북 브라우저에서 VM 주소:3000 으로 Grafana를 봄
        - ssh 접속 없어도 됨
            - ssh는 VM에서 내 명령어를 칠 때, 브라우저는 VM이 열어둔 화면만 볼때
            - Tailscale 내부망에서만 접속 가능
- 트러블슈팅 : 컨테이너별 그래프만 비어있음 → Docker 29 가 저장방식을 바꿔서 cAdvisor가 컨테이너를 찾지 못함 → cAdvisor가 리눅스 cgroup (커널이 컨테이너별 자원 사용을 세는 곳)을 직접 읽게 바꿈

### B. 환자 수별 측정

- 목적 : 환자 수를 늘려가며 어디서부터 지연이 무너지는지 찾음
- 설명 : 조건은 VM 4코어, 워커 3개, 워커는 메시지 1건에 3ms 일하는 척(가짜분석), 환자 수마다 30초
    - 결과 (끝단 지연 p95)
        - 6명 : 12\~13ms, 유실 0
        - 20명 : 22\~27ms, 유실 0
        - 50명 : 51\~54ms, 유실 0
        - 100명 : w1·w2는 101\~110ms인데, w0만 120ms → 1,010ms로 계속 늘어남
    - 100명 60초 다시 : w0 p95가 0.9초→ 1.9초까지 늘어남
        - VM CPU 약 78%, 워커 컨테이너 1코어 가득
    - 읽는 법 : 환자 수에 비례해서 지연이 늘다가 100명에서 w0 하나만 못 따라가고 무너짐 —> C에서 이유 찾음
    - 유실은 전부 0 —> 늦어져도 버리진 않고 큐에 쌓아둠

### C. 100명에서 w0만 밀린 이유

- 목적 : 100명에서 w0만 지연이 계속 늘어난 이유 찾기 (병목 찾기)
    - 병목 : 전체 흐름 중에 가장 느려서 전체를 막는 지점
- 설명 :  환자를 환자번호 % 3 으로 나누니깐 w0만 1명 더 받았고 그 1명 때문에 1초에 할 일이 1초를 넘어버림
    - 계산 : 100명 → w0 34명, w1,w2 33명씩
        - w0 : 34명 x 초당 10건 x 3ms = 1.02초 분량을 1초에 해야함 —> 못 따라가서 큐에 쌓임
        - w1, w2 : 33명 —> 0.99초
    - 결론 : 워커 하나 (1코어) 당 한계는 약 33명
    - 개선 방향 : 코어 많은 장비로 워커 늘리기 + 묶어서 처리 (배치) + 건당 처리 시간 줄이기
    - 후속 확인 (서버 담당 팀원 분석) : 3ms 가정 틀림
        - 실제 판정은 메시지마다가 아니라 5초 창 단위. 처음 5초가 모이면 1번, 그 뒤로는 창을 밀며 1초마다 한 번
            - 분석 1회 약 2.5ms → 환자 1명당 초당 약 2.5ms
            - 3ms 가정은 환자 1명당 초당 30ms (10건 X 3ms) → 실제보다 약 12배 무거움
        - 실제 CNN을 붙여 다시 잰 100명 : 유실 0, 판정 p95 약 102ms (맥북 기준)
    - 그래서 B표는 워커 한계를 넘으면 큐가 계속 쌓이는 결과 확인한 거로 남겨둠
    - 남은 일 : ecg VM에서 실제 분석 기준으로 다시 측정

### D. 환자 상태 화면 (시연용)

- 목적 : 서버 상태가 아니라 환자 판정 결과를 한 눈에 보려고 만든 화면
    - A 모니터링 = 서버가 괜찮은지 / D 모니터링 = 환자가 괜찮은지
- 설명 : 시연 워커가 9101번 포트로 환자 그리드 화면이랑 /metrics를 같이 내보냄
    - 그리드 : 환자마다 카드 하나
        - 정상이면 초록 / 이상 의심 빨강 / 판정 불가 회색 / 10초 넘게 신호 없으면 흐리게
    - Grafana ECG 환자 상태 (시연) 대시보드 : 이상 의심 환자 수, 환자별 상태, 상태 기록 타임 라인, 심박
    - 100명 띄워서 그리드 확인
    - 포트 정리
        - 9090 : Prometheus
        - 3000 : Grafana
        - 9101: 환자 그리드

### 트러블 슈팅

- 적체, 중복 숫자가 실제와 다름
    - 증상 : 100명 측정이 끝났는데 적체가 52,800으로 계속 늘어남.
        - 유실은 0인데 중복이 27,800건
    - 원인 1 (적체) : 큐 하나를 측정용 워커 (cg 그룹)랑 시연 워커 (demo 그룹)가 따로 읽는데, 수신부가 두 그룹의 안 읽은 걸로 합쳐서 셈
        - 시연 워커가 꺼져 있으면 그쪽 미처리분이 전부 적체로 잡힘
    - 원인 2 (중복) : 생성기를 다시 돌리면 seq가 0부터 새로 시작
        - 수신부는 번호가 1000 넘게 뒤로 가면 재시작으로 봤는데 30초 실행은 300까지만 올라가서 재시작으로 안 보고 전부 중복으로 계산
    - 해결 : 적체는 그룹별로 나눠 세고 운영 적체는 cg만 봄 / seq가 0으로 돌아오면 재시작으로 셈 / 단위 테스트 7개
- 100명 심박이 다 비슷함
    - 원인 : 100명 모두 같은 기록 (s30661) 1분을 시작 위치만 다르게 보냄.
        - 이상 의심도 환자 차이가 아니라 같은 파형의 다른 구간을 봄
    - 해결 : 생성기에 --records auto 옵션 추가
        - 환자마다 다른 3리드 기록을 보냄 —> 심박 범위 100\~120 → 65\~120
