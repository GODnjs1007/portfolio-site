### 목표

- 목적 : 팀원이 만든 수신부, Redis, 워커를 테스트 서버 (ecg VM)에 띄우고 내 생성기랑 연결해서 끝까지 이어지는지 확인. 시연용으로 R파 검출과 임시 AI판정까지 붙였음
    - 단계 흐름 : 3단계에선 보내는 구간만, 4단계에선 받아서 처리하는 데까지 처음으로 전부 연결함
- 흐름 : A: 수신부 , 큐, 워커 연결 → B: 시연용 R파 + 임시 AI → C: 시연 리허설
    - 서버 담당 팀원 :  수신부, Redis, 워커 코드
    - 나 : VM에 띄우기, 생성기 연결, 지연 측정, 시연용 R파 / 임시 AI, CNN 모델에 서버 붙이기
    - AI 담당 팀원 : 모델 학습
- 큰 그림
    - 생성기 → TCP 8000 → 수신부 → Redis —>워커 w0, w1, w2 (지연 측정)
        
                                                                             —>데모 워커 ( R파 + 임시 AI)
        

### A. 수신부, 큐, 워커 연결

- 목적 : 팀원 수신부, Redis, 워커를 VM에 띄우고 내 생성기를 붙여서 상자가 워커까지 빠짐없이 가는지 확인함
    - 3단계는 nc, 측정용 수신기라 받는 과정까지만 확인
        - 실제 구조로 끝단까지 처음 재는 단계
- 설명 : 도커 컴포즈로 3개를 한 번에 띄우고 생성기로 20명 X 10초 보냄 —> 2000개 전부 도착, 유실과 중복 검증 실패 0
    - 도커 : 프로그램을 필요한 환경째 상자 (컨테이너)에 담아서 어디서든 똑같이 돌리는 도구
    - 도커 컴포즈 : 컨테이너 여러 개를 파일 하나로 한 번에 켜고 끄는 도구
    - 워커 3개인 이유 : VM이 4코어, 워커 3개 + 나머지 1개는 수신부, Redis용
        - 코어 : CPU 안의 일꾼 수, 4코어면 동시에 4가지 일
    - 수신부가 하는 일 4가지
        1. 검사 : 필수 칸이 없거나 길이가 이상하면 세고 버리기. 멈추지 않는다. 
        2. 유실 세기 : 환자별로 직전 seq 기억
            - 5다음 8이 오면 유실 2
        3. 워커 배정 : channel_id % 3 —>환자 0,3,6은 w0 / 1,4,7은 w1 / 2,5,8은 w2
        4. 묶어서 올리기 : 50건씩 모아서 Redis에 한 번에 넣음
            - 안 차도 5ms 지나면 보내기
    - 같은 환자는 항상 같은 워커인 이유 : R파 검출이 환자 평소 R파 크기를 기억하면서 돌아감. 워커가 바뀌면 그 기억이 끊김
        - 샤딩 : 데이터를 규칙에 따라 여러 갈래로 나눠 담는 것
        - 적응형 임계값 : R파로 볼 기준선을 그 환자 신호 크기에 맞춰 계속 조절하는 것
    - Redis Streams : 워커마다 벨트 하나씩 총 3개 (ecg: s0, s1, s2)
        - XADD : 벨트에 상자 올리기 (수신부)
        - XREADGROUP : 벨트에서 상자 가져가기 (워커)
        - XACK : 처리끝의 확인, 확인이 없는 건 남아있어서 워커가 죽어도 다시 처리 가능
        - 적체 : 벨트 위에 쌓인 상자 수
            - 계속 늘면 워커가 못 따라가는 것.
    - 결과 : 워커별 처리 700 / 700 / 600 , 끝단 지연 p95 23\~27ms
    - 지연 두 종류
        - 보내는 구간 (3단계) : 생성기 → 받음
            - 100명 p95 : 3.2ms
        - 끝단 (4단계) : 생성기 → 수신부 → Redis 대기 → 워커 처리 끝
            - 20명 p95 : 23\~27ms
        - 목표 기준 2초는 끝단 쪽.
            - 지금은 2000ms의 약 1.3%
    - 한계 : 워커가 아직 3ms동안 일하는 척만 하는 껍데기고 진짜 분석이 붙으면 다시 측정
- 트러블슈팅
    - connection refused : 수신부 컨테이너가 다 뜨기 전에 생성기를 돌려서 뜸

### B. 시연용 R파 검출 + 임시 AI 판정

- 목적 : 정식 AI가 없어서 끝까지 이어지는 걸 보여주기 위해 시연용 R파 검출과 임시 AI를 붙였음
    - 정식 모델은 추후 ai담당 팀원이 만들어서 교체 예정.
- 설명 : 데모 워커가 환자별로 0.1초 상자 50개 (=5초) 를 모으면 —> R파 찾기 —> 숫자 10개 뽑기 —> 임시 AI로 판정 —> 한 줄 출력
    - 흐름
        
         생성기 —> 수신부 —> Redis —> 워커 3개 (지연측정)
        
                                                      —> 데모워커 (5초 모음 → R파 → 임시 AI → 출력)
        
        - 워커 3개는 판정 안 함. 상자 받고 3ms 쉬고 끝. 확인만 함 → 지연 측정용
        - 판정은 데모 워커 1개가 환자 전부를 혼자 함 —> C에서 처리 시간이 늘어난 이유
    - 컨슈머 그룹 : 같은 큐를 구독하는 모임.
        - 그룹이 다르면 같은 상자를 각자 받음
        - 데모 워커를 다른 그룹으로 둬서 기존 지연 측정에는 영향 없음
    - 파이프라인 : 생성기부터 판정까지 데이터가 차례로 거치는 길 전체
    - 5초 창 : [3, 1250] = 리드 3줄 X 숫자 1250개
        - 5초 이유 : 실시간이면 시간 기준이 입력 크기, 지연 관리에 유리 (조교 피드백)
        - 박동 기준이면 심박마다 길이가 달라짐
    - Pan-Tompkins : R파 찾는 방법
        - 잡음 거르기 → 가파른 곳 키우기 → 0.15초씩 묶어 봉우리마다 언덕 하나 → 기준선 넘는 언덕 = R파
    - 임시 AI가 보는 숫자 10개 : 심박, 박동 간격이 고른지, 박동 모양이 비슷한지, 박동 크기 / 폭
        - 조기 수축은 박동이 너무 일찍 와서 간격이 너무 짧아져서 간격 숫자로 잡음
    - 랜덤 포레스트 : 스무고개 나무 300개의 다수결로 판정
        - ex ) 심박 100이 넘음? —> 간격이 짧음? …
        - 딥러닝은 아니며 가볍고 학습이 몇 분이면 끝나서 임시용
    - 라벨 : 5초 안에 이상 박동 (V, A, S 등)이 하나라도 있으면 “이상 창”
        - LTSTDB에서 의사가 박동 하나에 붙여둔 정답 기호
            - N : 정상박동
            - V : 심실 조기 수축 (PVC) : 심실에서 먼저 튀어나온 박동
            - A : 심방 조기 수축 (APC) : 심방에서 예정보다 일찍 뛴 박동
            - S : 상심실성 조기박동 : 심실 위쪽 (심방 등)에서 일찍 뛴 박동
                - 공통점 : 셋 다 조기 박동임. 예정보다 일찍 뛴 박동
                    - AI가 박동 간격이 갑자기 짧아지는 걸 보고 잡을 수 있는 이유
                    - V는 모양까지 달라서 박동 폭, 모양 숫자로도 잡힘
    - 학습 , 평가 : 3리드 18명 X 30분 = 창 6480개  ,  13명으로 학습 , 처음 보는 5명으로 시험
        - 학습 목적 : 의사가 정답이라고 달아둔 데이터를 보고 AI가 이런 파형이면 이상이라는 기준을 스스로 만들게 함
        - 환자 단위로 나눈 이유 : 같은 사람으로 학습시키면 결과가 높아짐
        - 교차검증 : 학습용 13명을 4묶음으로 나눠 3묶음으로 배우고 1묶음으로 풀기를 해봄
        - 창 : AI가 한 번에 보고 판정하는 심전도 5초 묶음 (window)
            - 0.1초 상자 50개 = 1250개 샘플 X 3리드
    - 결과 : 민감도 0.93, 특이도 0.89
        - <mark>민감도 : 실제 이상 중 잡은 비율 (175/188)</mark>
        - <mark>특이도 : 실제 정상이고 정상이라고 한 비율 (1438/1612)</mark>
        - 미탐 : 이상인데 못 잡음 (13개)
        - 오탐 : 정상인데 잘못 울림 (174개)
        - 숫자는 전부 0\~1비율. 1=100%
    - 판정 기준을 0.5에서 0.20으로 낮춘 이유 : 미탐이 오탐보다 치명적이라 해서 우선적으로 설정.
        - 이상 확률 : AI가 5초 창마다 내는 점수 (0\~1)
        - 판정 기준 : 이상 확률이 몇 이상이면 이상으로 결정할지 정하는 기준
            - 판정 기준은 내가 정하는 값
            - 민감도는 돌려보고 나오는 결과 점수. 기준을 낮추면 민감도 상승
        - 0.5 : 기본값 (과반수) —> 거의 못 잡았음
        - 0.2 고른 방법 : 목표를 이상의 80퍼는 잡기로 정하고 교차검증으로 그걸 넘는 가장 높은 선 찾음 —> 0.2
            - 가장 높은 걸 고른 이유 : 선을 낮출수록 오탐이 늘어나서 목표만 넘으면 되는 최소한으로 잡음
    - 한계 : 오탐 174개라 실제 사용 수준이 안됨. 기록별 편차가 큼 (민감도 0.67\~1.00) 18명으로는 일반화 판단 어려움

### C. 시연 리허설

- 목적 : 생성기 → 수신부 → Redis → R파 → 임시 AI까지 한 화면에서 이어지는 걸 확인
- 설명 : 데모 워커를 켜고 환자 5명 X 30초를 보내서 5초마다 환자별 판정 줄이 찍히는 걸 확인
    - 실행 탭
        - 탭1 : `python demo_worker.py --shards 3`
        - 탭2 : `python stream_tcp.py 5 --seconds 30 --record s30661 --start-min 1`
    - 화면 읽는 법
        - 🔴 [환자 04] 5초 · R파 9개 · 심박 105 · 이상 의심 (0.59) · 처리 105ms
            - 누구 / 창 길이 / 박동 수 / 분당 박동 / 판정 / 이상 확률 / 마지막 상자 도착  —> 판정까지
            - 5초에 R파 9개면 심박 약 108, 숫자끼리 맞는지도 확인
    - 결과 : 30줄 중 이상 의심 12줄
        - 실제 이상 박동은 3개정도. 일부는 오탐
    - 처리 시간이 30 → 150ms로 증가
        - 5명 창이 동시에 차고 데모 워커 하나가 한 명씩 (약 25 ms) 처리해서 뒤 순서일수록 기다린 시간이 붙음 —> 그래서 워커를 여러 개로 나누는 구조의 필요
- 트러블 슈팅
    - R파 위치가 늦게 찍힘 : Pan-Tompkins가 묶는 과정 때문에 0.1초 늦은 위치를 돌려줌 —> 찍힌 위치 앞쪽에서 가장 큰 점으로 보정
    - 임시 모델 민감도 0 : 기록마다 리드 구성이 달라서 매번 다른 리드를 봄 + 판정 기준이 0.5로 너무 보수적 —> 리드를 신호 기울기로 자동 선택 및 기준을 교차 검증으로 고름 —> 민감도 0.00 → 0.93
