## 목표

생성기에서 나간 심전도가 서버까지 어떻게 갈지, 어떤 형식으로 보낼지 수신부 담당 팀원과 정한다. (10.5)

## 구성

```
생성기 → TCP 8000 (NDJSON) → 수신부 → Redis Streams → 워커 1개 (채널별 10초 모음) → R파 검출 → AI 판정
```

- 수신부: 상자를 받아 검사하고 큐에 넣는 접수 창구
- Redis Streams: 상자를 줄 세워두는 컨베이어(큐). 몰려도 서버가 안 죽게 해줌
- 워커: 큐에서 상자를 꺼내 분석하는 일꾼
- 채널: 환자 한 명의 심전도 줄. 채널 = 환자로 봐도 됨
- R파: 심전도에서 가장 뛰어오른 뾰족한 봉우리. 박동 하나에 하나

## A. 전송 방식: TCP

- 연결을 한 번 열어두고 계속 보냄. 순서가 지켜지고 중간에 빠지면 다시 보내줌
    - TCP: 컴퓨터끼리 데이터를 주고받는 규칙 중 하나. 도착 순서와 누락 재전송을 보장함. 반대로 UDP는 빠르지만 빠져도 모름
    - 8000: 포트 번호. 건물(컴퓨터) 안의 문 번호라고 보면 됨
- 여러 환자 메시지를 한 연결로 이어서 보내기 때문에 메시지 사이 경계가 필요 → NDJSON

### 자세히 보기

비유는 “심전도 택배 물류센터”로 통일함.

#### 1. 연결 방식을 왜 먼저 정해야 하나

- 보내는 쪽(내 생성기)과 받는 쪽(수신부)을 다른 사람이 만듦. 도로와 송장 양식을 안 정하면 각자 만들고 나서 안 맞음
- 정해두면 상대가 끝날 때까지 기다리지 않고 동시에 만들 수 있음 (실제로 10.8에 따로 만든 두 코드가 바로 붙음)

#### 2. TCP = 도로

- 한 번 길을 뚫어두면(연결) 상자가 보낸 순서대로, 빠짐없이 도착함. 중간에 사라지면 TCP가 알아서 다시 보냄
- 8000 = 문 번호(포트). 수신부가 8000번 문 앞에서 기다리고, 생성기가 그 문으로 찾아감
- 환자마다 도로를 따로 내지 않고 도로 하나에 전원 상자를 실음
- 응답(“잘 받았어”)을 안 받기로 한 이유: 한 건마다 답을 기다리면 왕복 시간이 매번 붙음. 1ms만 잡아도 1초에 1,000건이 한계인데 환자 100명이 딱 1초에 1,000건이라 여유가 0. 빠진 건 송장 번호로 셈

## B. NDJSON

- 한 줄에 JSON 하나, 줄바꿈(`\n`)이 메시지 끝 표시
    - JSON: `{"이름": 값}` 모양으로 데이터를 적는 글자 형식. 사람도 읽을 수 있음
    - NDJSON: Newline Delimited JSON. 줄바꿈으로 구분한 JSON
- 받는 쪽은 줄 단위로 자르기만 하면 됨

### 자세히 보기

#### 3. NDJSON = 상자 사이 칸막이

- 도로 하나에 상자가 줄줄이 붙어서 오니까 어디서 끊을지 약속이 필요함
- “줄바꿈 = 상자 하나 끝”. 받는 쪽은 줄 단위로 자르기만 하면 됨
- 덕분에 `wc -l`(줄 수 세기)만 해도 몇 개 왔는지 알 수 있음 (3단계)

## C. 메시지 형식 (임시안)

```json
{"channel_id": 0, "seq": 0, "t_start": 0.0, "sent_at": 1760000000.0, "fs": 250, "duration": 0.1, "leads": ["V4", "V3", "II"], "samples": [[...25개], [...], [...]]}
```

| 항목 | 뜻 | 쓰는 곳 |
| --- | --- | --- |
| channel_id | 환자(채널) 번호 | 누구 것인지, 워커가 채널별로 모을 때 |
| seq | 채널별 순번 | 빠진 번호 = 유실 |
| t_start | 이 조각의 측정 시작 시각 | 순서 맞추기 |
| sent_at | 보낸 시각 | 지연 계산 |
| fs, duration | 샘플링 속도, 조각 길이 | 받는 쪽에서 검사 |
| leads, samples | 리드 이름과 값 | R파 검출 입력 |
- 리드: 전극 조합으로 본 심장 방향. 3리드면 세 방향에서 본 그래프 3줄
- samples: 리드별 숫자 25개씩. `[[25개], [25개], [25개]]` = 3줄
- 임시안: 기업 장비 문서가 아직 없어서 우리끼리 정한 것. 문서 오면 바뀔 수 있음

### 자세히 보기

#### 4. 상자 하나 뜯어보기

```json
{"channel_id": 3, "seq": 57, "t_start": 5.7, "sent_at": 1791432323.07,
 "fs": 250, "duration": 0.1, "leads": ["V4","V3","II"], "samples": [[25개],[25개],[25개]]}
```

| 칸 | 택배로 치면 | 왜 필요한가 |
| --- | --- | --- |
| channel_id | 받는 사람(환자 번호) | 누구 심전도인지. 워커 배정 기준이기도 함 |
| seq | 송장 번호 | 0, 1, 3이 오면 2번이 빠진 거 → **유실**을 셀 수 있음 |
| sent_at | 발송 시각 | 받은(처리 끝난) 시각 − 발송 시각 = **지연** |
| t_start | 상자 안 내용물의 날짜 | 파형상 시각. 파일을 재생하니까 보낸 시각과 다름 |
| fs, duration | 내용물 규격 | 1초에 250번 측정, 이 상자는 0.1초 분량. 받는 쪽에서 검사용 |
| leads, samples | 내용물 | 리드 3개 × 25개 숫자. leads 순서가 samples 줄 순서 |

## D. 측정 방식

- 지연 = 워커 처리 완료 시각 − `sent_at`, p95(느린 쪽 5%를 뺀 최대값)로 봄
    - p95: 100개를 빠른 순서로 줄 세웠을 때 95번째. 평균은 아주 느린 몇 개를 가려버려서 p95를 봄
    - p50: 중간값. 절반은 이것보다 빠름
- 유실 = 채널별 `seq`가 빈 개수
    - 예: 환자 3번 상자가 0, 1, 2, 4로 오면 3이 빠짐 → 유실 1
- 개발 중에는 생성기도 같은 VM에서 돌림 → 시계가 같아야 시각 빼기가 맞음

### 자세히 보기

#### 5. 예상 질문

- seq, sent_at은 왜 넣었나? → seq는 순번이라 빠진 번호로 유실을 세고, sent_at은 보낸 시각이라 받은 시각에서 빼서 지연을 잼. 둘 다 없으면 부하테스트 자체가 불가능
- 생성기를 서버랑 같은 VM에서 돌리는 이유? → 시계가 같아야 sent_at 빼기가 맞음. 개발 단계는 같이, 최종 측정만 분리 (조교 피드백)
- 왜 MQTT 같은 걸 안 썼나? → 기업 장비가 실제로 뭘 쓰는지 문서가 아직 없음. 추측으로 정하지 않고 가장 단순한 TCP로 임시 연결. 문서 오면 수신부의 전송 부분만 교체
