title: "배운 점"
---

- A : AMI / 대상 그룹
  - AMI : 지금 돌아가는 서버의 이미지를 따둔 상태. 이 이미지로 찍어낸 서버는 Nginx가 이미 설치된 상태로 생성
    - 서버를 여러 대로 늘려야 하는데, 매번 EC2 만들고 Nginx 설치하는 걸 반복할 수 없어서 지금 상태를 통째로 이미지로 떠뒀다.
  - 그룹 대상 : ALB가 트랙픽을 보낼 서버 명단
    - 요청을 어떤 서버들에게, 몇 번 포트로 보내고 , 살아있는지 어떻게 확인할 것인가
    - ALB가 EC2에 바로 보내지않고 그룹대상을 걸치고 보낸다.
    - 대상 그룹을 만들 때 인스턴스를 직접 등록하지 않았다. ASG가 서버를 만들고 없앨 때마다 명단을 자동으로 갱신하기 때문에, 손으로 등록하면 오히려 어긋난다.
    - 상태 검사 경로를 `/`로 지정. ALB가 주기적으로 이 경로로 요청을 보내 서버가 살아있는지 확인한다.

- B : ALB 구성 및 보안 그룹 재설정
  - ALB (Application Load Balancer) : 하나의 주소로 들어온 HTTP 요청을 여러 서버에 나눠서 전달하는 AWS의 로드 밸런서
    - Application : 애플리케이션 계층(HTTP/HTTPS)의 내용을 이해하고 처리한다는 뜻
    - Load Balancer : 부하(Load)를 여러 서버에 고르게 나누는(Balance) 장치
  - ALB의 보안그룹 : EC2와 공유하지 않으므로 따로 생성
  - ALB의 가용영역 : 2개 이상 설정
    - ALB가 AZ 한 곳에만 있으면, 그 AZ가 죽었을 때 **뒤에 서버가 아무리 많아도 입구가 사라져 서비스가 멈춘다.**
  - 리스너 : **몇 번 포트로 들어온 요청을 어디로 보낼지** 정하는 규칙
    - 사용자 요청 (port : 80) —> 리스너 → 그룹 대상 (nginx-tg)
  - EC2의 보안그룹 재설정
    - HTTP 인바운드 설정을 ALB로 수정
      - 전에는 사용자가 EC2에 직접 접속해야 했기 때문에 80번을 전체에 열어둘 수밖에 없었지만, ALB를 붙인 뒤에는 모든 정상 요청이 ALB를 거쳐 오므로 소스를 ALB 보안 그룹으로 변경
      - EC2의 80번이 여전히 전체에 열려 있으면, 누군가 EC2의 IP를 알아내 ALB를 건너뛰고 직접 접속할 수 있다. 그러면 ALB에서 하는 검사나 제어를 전부 우회하게 된다.
    - 소스에 IP가 아니라 보안 그룹을 지정한 이유
      - ALB는 내부적으로 여러 IP를 쓰고 AWS가 바꾼다. IP로 지정하면 바뀔 때마다 고쳐야 하지만, 보안 그룹으로 지정하면 "이 그룹에 속한 것"이라는 관계로 판단하므로 손댈 필요가 없다.

- C : Launch Template · Auto Scaling Group 구성
  - Launch Template : EC2 인스턴스를 만들 때 사용할 설정을 미리 정의해둔 설계도.
    - 새 서버를 만들려면 결정해야 하는 것들을 미리 적어두는 것 (AMI, 인스턴스 유형, 키페어, 보안그룹)
    - 무엇을 만들지만 정의, 서버를 어디에 둘 것은 ASG가 정의
  - ASG : Auto Scaling Group
    - 지정한 대수를 유지하도록 인스턴스를 **자동으로 만들고, 없애고, 교체하는** 그룹
    - 지정된 서브넷들에 **최대한 고르게 나눠서** 배치
      - 희망 용량 : 평소에 유지할 대수. 이보다 적어지면 자동으로 채운다
      - 최소 용량 : 부하가 없어도 이 아래로는 줄이지 않는다
      - 최대 용량 : 부하가 몰려도 이 위로는 늘리지 않는다 (비용 상한)

      | 희망 용량 | 서브넷 | 결과 |
      | --- | --- | --- |
      | 2 | 2a, 2b | 각 AZ에 1대씩 |
      | **4** | 2a, 2b | 각 AZ에 2대씩 |
      | **1** | 2a, 2b | 둘 중 한 곳에 1대만 |
      | 2 | **2a만** | 2a에 2대 몰림 |

    - ELB 상태검사
      - ALB가 내린 Unhealthy 판정을 ASG가 받아들인다**.** 그래서 "인스턴스는 살아있지만 웹서버가 응답하지 않는" 상황에서도 서버를 교체할 수 있다.
  - \[요청 흐름\]          사용자 → ALB → 대상 그룹 ─┐<br>                                                                           ├→ EC2<br>\[생성 흐름\]  AMI → Launch Template → ASG ┘

- D : 검증 및 리소스 정리
  - 트래픽 분산 : 2a, 2b 서버에 각각 index.html을 다르게 입력 후 웹페이지 새로고침하면서 확인 —> 변갈아가면서 바뀐 내용들 나오는 거 확인
  - 장애 자동 복구 : 2a 서버 중지시킴 → 502 오류 페이지랑 2b 서버 페이지 두 개가 번갈아가면서 나오다가 최종적으로 2b 서버 index.html만 나옴.
    - ALB의 헬스체크는 주기적으로 하고 연속 실패가 쌓여야 Unhealthy 판정을 내린다.
      - 판정 전까지는 죽은 서버에도 계속 트래픽을 보내서 502가 났고, 판정 후 제외되면서 사라졌다.
    - 대상그룹의 변화
      - 2a 서버 → `Draining` (처리 중인 요청만 마무리하고 명단에서 빠지는 중)
      - ASG가 새로 만든 서버 → 헬스체크 통과 후 `Healthy`로 명단에 합류
    - ASG가 새로 만든 서버에는 서버 A/B (다르게 입력한 구문) 구분 문구가 없었다.
      - AMI가 문구 수정 이전에 만들어졌기 때문. 서버에 손으로 고친 건 인스턴스가 교체되면 사라진다.
