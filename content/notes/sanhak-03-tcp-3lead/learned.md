### 목표

- 목적 : 1단계 생성기에 TCP 전송을 붙이고 (비어있는 send함수 채우기), 기업 장비에 맞춰 3리드 데이터로 채움
    - 단계 흐름 : 1단계 = 만들기만, 2단계 = 보내기 규칙 정하기 , 3단계 = 실제로 보내보기
- 흐름 : A: 3리드 찾기 → B: 생성기에 TCP 전송 붙이고 → C: nc로 도착하는지 확인 → D: 측정용 수신기로 환자 수별 유실, 지연 측정

### A. 3리드 데이터 조사

- 목적 : 기업 장비가 3리드라서 공개 데이터 중에 3리드 기록 찾아봄
    - 1단계에서 사용한 s20011은 2리드
- 설명 : LTSTDB 안에서 3리드 기록 18개 (s30661\~s30801)을 찾아서 사용
    - 다른 공개 데이터도 같이 조사해서 용도 나눴음
    - 기록 이름 규칙 : 첫 숫자가 리드 수
        - s2xxxx : 2리드 / s3xxxx : 3리드
    - 3리드 : 전극 3개로 심장을 세 방향에서 본 그래프 3줄
    - 12리드 : 병원 정밀 검사용 12방향.
        - 여기서 3개 골라 사용 가능
    - 데이터별 용도
        - LTSTDB s3 기록 : 3리드, 250Hz, 하루치 → 스트림 / 부하테스트
        - INCART : 12리드 중 3개 사용, 257Hz , 30분 X 75개 —> AI 정확도 평가
        - PTB-XL : 12리드, 500Hz, 10초짜리 2만개 이상 —> AI 학습
        - 내 파트는 길게 흘려보내는 게 중요해서 LTSTDB사용
            - AI 팀은 정답이 달린 데이터가 필요해서 INCART, PTB-XL 사용
    - 라벨 : 박동마다 붙어 있는 정답 (정상인지, 어떤 부정맥인지)
        - AI를 학습시키고 채점하는 데 필요
    - 리샘플링 : 측정 간격이 다른 데이터를 250Hz로 맞추는 작업
        - INCART(257Hz), PTB-XL(500Hz)는 그대로 못 쓰고 맞춰야 함

### B. TCP 생성기 (stream_tcp.py)

- 목적 : 1단계 생성기에 비어있던 send() 함수를 채워서 실제로 TCP로 서버에 보내게 만듦
    - 1단계는 만들기만 하고 보내지 않음. 2단계에 정한 규칙으로 진짜 보내보는 단계
- 설명 : 서버에 한 번 연결해두고 0.1초마다 환자 N명분 메시지를 만들어 한꺼번에 보내봄
    - 흐름 : 연결 한 번 → 0.1초마다 [환자별로 25개 X 3리드로 자름 → 송장 붙여서 메시지 만듦 → 글자로 바꾸고 \n 붙이기] → N명분을 이어 붙여 한 번에 전송 → 다음 박자까지 대기 (1단계 next_tick 그대로)
    - 실행
        
        ```bash
        python stream_tcp.py 100 --host 127.0.0.1 --port 8000 --record s30661 --seconds 10
        ```
        
        - `--host` : 보낼 주소. 127.0.0.1 = 자기 자신(같은 컴퓨터).
            - 다른 컴퓨터로 보내려면 그 컴퓨터 주소
        - `--port` : 보낼 문 번호 (8000)
        - `--record` : 재생할 기록 (3리드인 s30661)
        - `--seconds` : 몇 초 동안 보낼지
    - socket : 프로그램끼리 네트워크로 대화하는 창구
        - TCP를 사용하는 창구
        - 프로그램이 운영체제한테 이 주소와 문으로 연결해주게 부탁하는 창구
            - 연결의 한쪽 끝
    - sendall : 가진 데이터를 끝까지 다 보낼 때까지 보내는 함수
        - 창구에 대고 보내달라고 하는 명령
        - 소켓에 데이터를 넣으면 실제로 보내는 일은 운영체제가 TCP 규칙대로 함
        
        ![sendall(데이터) → 소켓 ═ TCP 연결 ═ 소켓 → readline(). 인사·순서·재전송은 운영체제가 처리](img-learned-01.webp)
        
    - 한 번에 묶어 보내는 이유 : 환자마다 따로 보내면 0.1초에 100번 보내야 하기 때문에 묶으면 1번으로 가벼움
    - seq : 환자별로 보낼 때마다 1씩 늘림 —> 받는 쪽이 유실 확인
    - sent_at : 보내는 순간의 시각을 찍음 —> 받는 쪽이 지연 계산
    - 받는 쪽이 끊기면 : 멈추고 지금까지 보낸 개수 출력
- 트러블슈팅
    - 시간 기준으로 반복했더니 10개 더 보내는 버그 —> 횟수 기준 (10초=100번)으로 바꿈

### C. 확인 (nc)

- 목적 : 팀원 수신부 없이도 생성기가 제대로 보내는지 먼저 확인
    - 받는 쪽까지 같이 돌리다 문제 생기면 보내는 쪽인지 받는 쪽인지 구분이 힘듦
- 설명 : nc로 8000번 문을 대신 열어서 받는 척 하게 하고 생성기로 보내서 받은 줄 수를 셈
    - nc (netcat) : 받는 서버를 흉내 내는 도구
        - 문을 열고 들어온 걸 그대로 받아줌
    - 실행 : 터미널 탭 2개 (둘 다 VM 접속)
        - 탭 1 (받는 쪽) —> 8000번 열고 기다리다가 받은 줄 수를 셈
            
            ```bash
            nc -l 8000 | wc -l
            ```
            
            - -l : listen : 문열고 기다림
            - | (파이프) : 앞 명령의 결과를 뒤 명령으로 넘김
            - wc -l : 줄 수 세기.
                - NDJSON은 한 줄 = 메시지 1개라서 줄 수 =  받은 개수
        - 탭 2 (보내는 쪽)
            
            ```bash
            python stream_tcp.py 10 --seconds 5
            ```
            
    - 결과
        - 1명 X 2초 : 메시지가 형식 그대로 도착
        - 10명 X 5초 : 500개 보내고 500개 받음 —> 유실 0 (10명 X 1초에 10개 X 5초)
        - 100명 X 3초 :  3000개 보내고 3000개 받음 —> 최대 지각 18ms
    - 3리드 확인 : s30661을 읽어보니 리드 V4·V3·II, 250Hz, 표 모양 (2500, 3) = 10초 × 3리드
        - A에서 고른 기록이 VM에서 제대로 읽히는지 보내기 전에 확인. 250Hz라 생성기 박자는 그대로 씀
        - 리드 이름은 기록마다 다름 (다른 기록은 E-S, A-S, A-I) → 그래서 실제 장비 조합 확인이 남은 작업
    - ecg VM : 미니 PC 안에 만든 산학 전용 컴퓨터에서 테스트
        - 코드가 여기 있어서 이 공간에서 테스트
        - 실행 순서 : 노트북 터미널에서 ssh로 VM접속
        - host 127.0.0.1 : 생성기랑 받는 쪽이 둘 다 VM 안이라 자기 자신에게 보냄
            - 시계가 같아야 하기 때문에 같은 VM에서 돌림
    - 한계 : 도착과 몇 개인지만 확인. 지연과 유실을 seq, sent_at로 계산하지 않음

### D. 측정용 수신기와 환자 수별 측정

- 목적 : 받는 쪽에서 유실, 지연을 실제로 계산해서 환자수를 늘려도 보내는 구간이 버티는지 확인
    - C(nc)는 개수만 셌고 2단계에서 정한 기준 (유실, 지연 P95)을 실제 숫자로 뽑아서 확인
- 설명 : 측정용 수신기 (measure_recv.py)를 직접 만들어 8000번에 받게 하고 환자 6,20,50,100 명으로 각각 10초씩 보냄
    - 측정용 수신기 : nc 대신 쓰는 받는 쪽 프로그램.
        - 받으면서 seq, sent_at을 보고 계산하고 끝나면 결과 출력
    - 실행 (둘 다 VM접속)
        - 탭 1 : python measure_recv.py (받는 쪽)
        - 탭 2 : python stream_tcp.py 100 --seconds 10 (보내는 쪽)
    - 출력하는 것
        - 지연 : 받은시간 - sent_at. p50 / p95 / 최대로 봄
        - 유실 : 환자별로 seq가 빠진 개수
        - 순서 뒤바뀜 : 5번 다음에 4번이 온 경우
            - TCP라 보통은 0임
        - 처리량 : 1초에 받은 상자 수
            - 환자수 X 10 이면 정상
    - 결과
        - 6명 : 600/600, 유실 0, p95 0.5ms
        - 20명 : 2,000/2,000, 유실 0, p95 0.9ms
        - 50명 : 5,000/5,000, 유실 0, p95 1.8ms
        - 100명 : 10,000/10,000, 유실 0, p95 3.2ms, 처리량 1,010개/초
        - 읽는 법 : 100명까지 하나도 빠지지 않았고 늦어도 3ms정도임. 환자가 늘수록 지연은 조금씩 늘지만 기준 (2초)에 비하면 아주 작은 편
        - ms : 밀리초 (1/1000초) —> 3.2ms = 0.0032초
    - 한계 : 보내고 받는 구간만 재고 큐, 워커 처리시간은 빠져있어서 실제 부하테스트는 워커 붙인 4단계 이후 다시 확인
